Oftentimes Redux actions are treated as **state setters** instead of **describing events**.

## Example

Consider a restaurant app scenario where someone orders a pizza and a bottle of Coke. You could dispatch an action like an:

### Event

> Hey, someone ordered a pizza and a pop, deal with it somehow.

```javascript
dispatch({ type: "food/orderAdded", payload: { pizza: 1, coke: 1 } });
```

### State Setter

> Set the pizza and coke current values to specific numbers.

```js
dispatch({
    type: "orders/setPizzasOrdered",
    payload: { amount: getState().orders.pizza + 1 },
});

dispatch({
    type: "orders/setCokesOrdered",
    payload: { amount: getState().orders.coke + 1 },
});
```

### Evaluation: Redux Actions as Events vs. Setters

#### Event Approach:

- Only requires a single action to be dispatched.
- Offers flexibility: you can specify the number of ordered pizzas/cokes.

#### Setter Approach:

- Involves dispatching multiple actions to update the state correctly.
- Requires more knowledge about the state's structure.

#### Additional Benefits of the Event Approach:

- **More meaningful action names:** Enhances code readability and understanding.
- **More meaningful action log history:** Facilitates debugging and tracking changes.
- **Fewer issues with asynchronous state updates:** Reduces potential conflicts and improves reliability.
